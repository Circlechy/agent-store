# Agent 场景与技术方案设计

## 1. 业务场景 (Business Scenario)

在软件工程自动化（SWE-Agent）、代码评估（Evaluation）、以及持续集成（CI/CD）等场景中，**"为任意 Python 仓库构建一个可运行的开发环境"** 是一个极具挑战性的基础任务。

**主要痛点：**
*   **依赖描述不统一**：有的项目用 `requirements.txt`，有的用 `setup.py`，有的用 `environment.yml`，甚至只有 `README.md` 中的自然语言描述。
*   **版本冲突**：依赖包之间经常存在版本不兼容，导致直接安装失败。
*   **环境验证困难**：安装成功不代表能运行，经常出现 `ImportError` 或动态链接库缺失。
*   **操作系统的差异**：Windows 和 Linux 下的构建命令和路径处理方式不同。

**本 Agent 的目标**就是解决上述痛点，提供一个**全自动、高鲁棒性**的环境构建服务，为后续的 AI 编码助手（如自动修复 Bug、自动写单测）提供坚实的运行时基础。

---

## 2. 技术方案 (Technical Architecture)

本方案基于 **OpenJiuwen** 框架，采用了 **分层工作流（Hierarchical Workflow）** 以及 **多智能体协作 (Multi-Agent)** 的设计架构。

### 2.1 整体架构

系统采用串行编排模式，将复杂的构建任务拆解为五个独立的子任务（Sub-Agent）：

```
┌─────────────────────────────────────────────────────┐
│                   用户输入层                        │
│         (仓库URL/本地路径/环境配置需求)            │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│               主控协调层                            │
│  • 任务编排(Task Orchestration)                    │
│  • 状态管理(State Management)                      │
│  • 错误处理(Error Handling)                        │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│            Agent执行层                              │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐     │
│  │Git Clone   │ │Planning    │ │Build       │     │
│  │Agent       │ │Agent       │ │Agent       │     │
│  └────────────┘ └────────────┘ └────────────┘     │
│  ┌────────────┐ ┌────────────┐                    │
│  │Test Agent  │ │Save Agent  │                    │
│  └────────────┘ └────────────┘                    │
└─────────────────────┬───────────────────────────────┘
                      │
┌─────────────────────▼───────────────────────────────┐
│             工具与服务层                            │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐    │
│  │Git工具│ │文件读取│ │命令执行│ │环境管理│ │日志服务│  │
│  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘    │
└─────────────────────────────────────────────────────┘
```

### 2.2 核心模块详解

#### 1. Git Clone Agent
*   **功能**：负责将目标代码仓库完整拉取到本地工作空间，支持鉴权和错误重试。
*   **实现流程**：
    1.  **环境检查**：检查目标文件夹是否存在，避免重复拉取。
    2.  **克隆循环**：尝试执行 `git clone` 命令，支持自动注入 GitHub Token。
    3.  **结果校验**：检查操作结果，如果成功则跳出循环；如果失败（如鉴权错误、网络超时），则进入错误处理分支。
    4.  **智能修复**：LLM 分析 Git 报错信息，修正仓库 URL 或生成前置命令（Precommand），然后更新参数并重试。

#### 2. Planning Agent
*   **功能**：分析仓库文档和配置文件，生成构建环境所需的名称、Python 版本和安装命令。
*   **实现流程**：
    1.  **文档扫描**：优先读取 `README.md` 等文档，精准提取开发者建议的 "Installation" 章节。
    2.  **基于 README 规划**：LLM 分析文档片段，提取原汁原味的安装命令（保留所有参数和标志），并推断环境名称与 Python 版本。
    3.  **校验与兜底**：系统校验生成的计划。如果文档信息缺失或生成的计划不完整，则回退扫描 `environment.yml`、`requirements.txt` 等配置文件，再次通过 LLM 生成标准构建计划。

#### 3. Build Agent
*   **功能**：负责执行环境创建和依赖安装指令，具备自我修复能力。
*   **实现流程**：
    1.  **环境创建循环**：执行 `conda create`。若失败，LLM 分析错误（如版本不支持），修正参数并重试（最多 3 次）。
    2.  **依赖构建循环**：执行规划阶段生成的安装命令。
    3.  **自愈机制**：若安装过程报错（如缺失系统库、依赖冲突），LLM 分析 `stderr` 日志，生成修复命令（如安装 `build-essential`）或调整安装参数，并自动重试构建。

#### 4. Test Agent
*   **功能**：进行环境安装结果验证。
*   **实现流程**：
    1.  **依赖再扫描**：重新扫描仓库中的所有依赖配置文件。
    2.  **LLM 代码生成**：生成一个健壮的 Python 验证脚本（包含 import 检查和错误捕获）。
    3.  **沙箱执行**：在构建好的 Conda 环境中运行该验证脚本。
    4.  **LLM 裁判**：分析脚本的输出日志，判定哪些包通过了验证，生成最终的 JSON 测试报告。

#### 5. Save Agent
*   **功能**：保存环境安装依赖以供下次使用。
*   **实现流程**：
    1.  **conda 环境保存**：使用conda export命令导出环境。

#### 5. Infrastructure (基础设施)
*   **组件化**：所有底层操作（文件读写、命令执行）封装为 `Component`，易于测试和复用。
*   **跨平台兼容**：函数自动检测当前 Shell（PowerShell, CMD, Bash），并适配命令。
